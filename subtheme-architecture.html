🔍 Architecture Reference

Sub-theme Generation

A precise technical walkthrough of how sub-themes are generated, from vector document retrieval through LLM map-reduce prompting, mention scoring, and caching. Written for developers making architectural changes.

System View

Full Pipeline Diagram

The sub-theme lifecycle involves 5 stages. Sub-themes are not pre-defined — they are emergent from the LLM reading student survey responses.

Step 1

Document Retrieval

The first decision point: how are relevant student responses selected? This depends on whether the request is for a parent theme or a sub-theme drill-down. Both paths go through _select_theme_documents() in service.py.

🏠 Parent Theme

Uses collect_theme_documents(). Queries ChromaDB for documents where theme_primary == theme_name (definite evidence) plus documents flagged theme_ambiguous == True that have this theme as a candidate (ambiguous evidence).

Documents are pre-classified during embedding — this is NOT a semantic search. It's a metadata filter lookup.

🔍 Sub-theme Drill-down

Uses collect_documents_by_query(). The sub-theme name (e.g. "Curriculum Coherence") is embedded as a vector and used for semantic similarity search across the entire collection (with any active filters applied).

Results are reranked and capped at n_results (default 500). Low-information responses are filtered out.

💡

Key distinction: Parent themes use classification-based retrieval (docs were assigned to themes at embedding time). Sub-theme drill-downs use live semantic search (the sub-theme name is the query). This means a sub-theme drill-down may return documents from any parent theme if they're semantically close to the sub-theme name.

Document Cap

After retrieval, documents are capped at HIERARCHICAL_RAG_MAX_DOCUMENTS (default: 240). If a max_documents override is passed in the API request, that takes priority. Setting this to 0 means no cap — use all retrieved documents.

# service.py line 106 cap = max_documents if max_documents and max_documents > 0 else HIERARCHICAL_RAG_MAX_DOCUMENTS
Step 2

LLM Prompting

Sub-themes are extracted by instructing the LLM to identify them while reading student responses. There are three prompt templates. The one used depends on whether the corpus fits in a single context or requires batching.

Single-prompt Mode (default_prompt)

Used when ≤60 documents. The full evidence set fits in one LLM call.

You are an expert data analyst. Read the following student survey responses about '{theme_name}'.
Theme scope: {THEME_LLM_DEFINITIONS[theme_name]}

Only analyze comments as evidence for this theme. Do not drift into Support / Mentoring unless the selected theme is Support / Mentoring.
Write generated fields in English: summary, sentiment points, positive_comments, critical_comments, and subthemes. Keep only student_suggestions as exact verbatim student comments in their original language.

Summarize the general consensus in 2 sentences. Extract 3 key sentiments...
Also extract 3 to 5 short sub-themes or topics mentioned.

Respond EXACTLY in this JSON format:
{ "summary": "...", "sentiments": [ {"sentiment": "Positive", "point": "..."} ], "positive_comments": ["..."], "critical_comments": ["..."], "student_suggestions": ["..."], "subthemes": ["...", "..."] }
⚠️

The sub-theme instruction is minimal: just "extract 3 to 5 short sub-themes or topics mentioned". There is no definition, no examples, no constraints on naming. The LLM has total freedom to choose names, granularity, and scope.

Batch (Map) Prompt (build_batch_summary_prompt)

Used for each batch of 60 documents during the map step. Identical sub-theme instruction, but with additional context:

You are analyzing batch {i} of {N} for the survey theme '{theme_name}'.

This is an intermediate map step, not the final theme summary. Summarize only this batch without making whole-theme prevalence claims.

Respond EXACTLY in this JSON format:
{ "summary": "...", "sentiments": [...], "positive_comments": ["..."], "critical_comments": ["..."], "student_suggestions": ["..."], "subthemes": ["...", "..."] }

Each batch independently produces 3–5 sub-theme labels. Different batches will likely produce overlapping but inconsistently named sub-themes (e.g. "Workload Issues" vs "Heavy Workload" vs "Study Load").

Reduce Prompt (build_reduce_prompt)

Receives ALL batch JSON summaries serialized as a JSON array. Asks the LLM to merge them:

Merge the batch-level survey insights for '{theme_name}' into one final dashboard insight.

The batch summaries together represent {N} source student responses.
Only make claims supported by repeated or strong evidence. Do not invent quotes or details.

Deduplicate repeated points across batches. Prefer patterns that appear in multiple batches, but keep a strong minority concern if it is concrete and important.

Also extract 3 to 5 short sub-themes or topics mentioned across the batch summaries.

Batch summaries:
[ { "batch_number": 1, "source_document_count": 60, "summary": "...", "subthemes": ["Workload Issues", "Portfolio System", "Feedback Quality"], ... }, { "batch_number": 2, "source_document_count": 60, "summary": "...", "subthemes": ["Study Load", "Assessment Clarity", "Feedback Quality"], ... } ]
🔴

The reduce step deduplication is entirely done by the LLM — there is no code-level deduplication of sub-theme names. The LLM reads all batch-level sub-theme arrays and decides which to keep, merge, or drop. If the LLM doesn't notice "Workload Issues" and "Study Load" are the same concept, both end up in the final list.

How Evidence is Appended to Prompts

The _append_evidence() function splits documents into two labeled sections within the prompt:

# Definite evidence (theme_primary match or free-text retrieval) Definite evidence: - Student comment 1... - Student comment 2... # Ambiguous evidence (close classification candidates) Ambiguous candidate evidence: These responses were close classification candidates for this theme. Ignore any candidate evidence that is not genuinely relevant. - Student comment 3...

The LLM is told to use ambiguous evidence with caution. For sub-theme drill-downs, all documents come as free_text_retrieval type and appear in the definite section.

Step 3

Map-Reduce Flow

The function _generate_hierarchical_json() orchestrates the LLM calls. The batch size and the decision logic are straightforward.

Single vs Batched Decision

def _generate_hierarchical_json(client, llm_model, theme_name, evidence, ...): batches = _document_batches(evidence) # chunks of 60 if len(batches) <= 1: # ≤60 docs: single prompt, done prompt = prompts.build_prompt(theme_name, evidence) return prompts.parse_llm_json(client.generate_json(llm_model, prompt)) # >60 docs: map-reduce # ... (see map and reduce steps below)
📊

Example: 180 documents → 3 batches of 60 → 3 LLM map calls + 1 LLM reduce call = 4 total LLM calls.
240 documents (default cap) → 4 batches → 5 LLM calls.
55 documents → 1 batch → 1 LLM call (no reduce needed).

R

The LLM reads every batch's subthemes array and produces one final merged list.

The LLM is the deduplicator. It sees: ["Topic A", "Topic B", "Topic C"] + ["Topic A", "Topic D", "Topic E"] + ["Topic B", "Topic D", "Topic F"]
And might produce: ["Topic A", "Topic B", "Topic D", "Topic E"]

Step 4

Mention Counting

After the LLM produces the final subthemes array, subtheme_mention_rows() counts how many of the ALL source documents (not just the batched ones) mention each sub-theme. This scoring is entirely deterministic and code-based — no LLM involved.

Matching Algorithm

For each LLM-generated sub-theme label, the algorithm:

1
Tokenize the sub-theme label
Lowercase, extract alphanumeric tokens, remove stopwords (EN + NL), keep tokens with length > 3.
Example: "Curriculum Coherence and Relevance" → ["curriculum", "coherence", "relevance"]
2
Generate 6-char prefix roots
For tokens longer than 6 chars, take the first 6 characters as a stem.
Example: "curriculum" → root "curric", "coherence" → root "cohere"
3
Scan every document
A document is a "mention" if any of these match:
a) The full lowercase label appears as a substring: "curriculum coherence and relevance" in doc
b) Any token appears as a whole word in the document: "coherence" in doc_words
c) Any word in the document starts with a 6-char root: word.startswith("curric")
4
Compute percentages
doc_percentage = mentions / total_docs × 100
percentage = mentions / total_mentions_across_all_subthemes × 100
⚠️

Matching is very loose. The root-prefix approach means "curriculum" will match "curriculumherziening" (Dutch for curriculum revision). Token matching means a sub-theme label "Communication" will match any document containing the word "communication" even if the context is unrelated. The matching rules use OR logic — any single match counts.

The function is called in _theme_payload_from_parsed():

# service.py line 413 "subtheme_mentions": insight_metrics.subtheme_mention_rows(subthemes, all_docs),

Note: all_docs here is the full set of retrieved documents (before the batch cap), not just the documents that were sent to the LLM. So if 500 documents were retrieved but only 240 went to the LLM, mentions are counted across all 500.

Step 5

Caching

Generated payloads (including sub-themes) are cached to gemma_cache.json on disk. Cache logic lives in cache.py.

Cache Key Structure

ScenarioCache Key Format
Parent theme, no filters "Content and Organisation"
Parent theme + filters "Content and Organisation::filters={\"academic_year\":\"2024/2025\"}"
Sub-theme drill-down "Content and Organisation::subquery=Curriculum Coherence"
Sub-theme + filters "Content and Organisation::subquery=Curriculum Coherence::filters={...}"
# service.py line 54 def _cache_key(theme_name, filters=None, theme_query=None): key = theme_name if theme_query and theme_query != theme_name: key = f"{theme_name}::subquery={theme_query}" if not normalized: return key return f"{key}::filters={filters_json}"

Cache Invalidation

A cached entry is considered valid when all of these match:

  • cache_version == INSIGHT_CACHE_VERSION (currently 11)
  • llm_context_documents == current LLM_CONTEXT_DOCUMENTS setting
  • hierarchical_batch_documents == current HIERARCHICAL_RAG_BATCH_DOCUMENTS setting
  • All classification metadata matches (embedding model, reranker, theme taxonomy version)
  • If match_llm_identity=True: llm_provider and llm_model must match
  • Filter values must match
💡

Changing the batch size, the cache version, or the LLM model will automatically invalidate all cached entries. The cache check happens before any LLM call. If the cached entry passes validation, no LLM call is made at all.

For parent themes, the cache is checked with full dashboard field validation (requires subthemes, subtheme_mentions, quotes, etc. to all be present). For sub-theme queries, only the generation settings are checked.

Step 6

Precompute Flow

The POST /api/precompute-insights endpoint generates summaries for all themes in batch. It streams NDJSON progress events. There's a specific sub-theme pre-caching feature.

Sub-theme Pre-caching

When precache_subthemes: true is set in the request, after generating a parent theme summary, the system takes the LLM-generated subthemes array and makes an additional _generate_theme_payload() call for each sub-theme:

# service.py line 648–702 if precache_subthemes: subthemes = [ str(s).strip() for s in (response_data.get("subthemes") or []) if str(s).strip() and str(s).strip() != theme_name ] for subtheme in subthemes: sub_data = _generate_theme_payload( ..., theme_query=subtheme, # ← triggers collect_documents_by_query ) cache[_cache_key(theme_name, combo, subtheme)] = sub_data

This means each sub-theme gets its own: semantic retrieval → batching → LLM map-reduce → mention counting → cache entry. And those sub-theme results themselves contain a subthemes field — creating the potential for recursive sub-sub-themes.

⚠️

Cost implication: With 7 themes × 4 sub-themes each × N filter combinations, pre-caching sub-themes can multiply LLM calls dramatically. Each sub-theme may itself trigger 4+ LLM calls (if it retrieves enough documents for map-reduce).

Key Takeaways

What to Know Before Changing the Architecture

Critical Design Decisions
  1. Sub-themes are 100% LLM-generated. No pre-defined taxonomy. The prompt says "extract 3–5 sub-themes" and the LLM decides what they are. Different runs with the same data may produce different sub-theme names.
  2. Deduplication in map-reduce is 100% LLM-handled. The reduce prompt tells the LLM to "deduplicate repeated points across batches" but there is no code that normalizes, clusters, or fuzzy-matches sub-theme names.
  3. Mention counting is keyword-based, not semantic. After the LLM generates sub-theme labels, subtheme_mention_rows() does naive token/prefix matching against all docs. A sub-theme called "Communication" will match any doc with that word regardless of context.
  4. Sub-theme drill-down uses a completely different retrieval path. Parent themes use classification-based lookup; sub-themes use semantic vector search. This means a sub-theme drill-down may pull in documents from other themes.
  5. The cache is keyed on exact sub-theme name strings. If you regenerate parent themes and the LLM produces slightly different sub-theme names, old sub-theme cache entries become orphaned and will never be served.
  6. Sub-theme results themselves contain sub-themes. When you drill into a sub-theme, the LLM generates sub-sub-themes. The frontend renders these via SubthemesList — creating a recursive navigation pattern with no depth limit in the data.
